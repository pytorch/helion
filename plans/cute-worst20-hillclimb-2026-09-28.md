# CuTe worst-20 hillclimb (run `worst20-2026-09-28`)

Target: the 20 kernel types where the Helion CuTe backend was furthest behind
the best external baseline in `artifacts/backend-study-2026-09-23/full/report`
(ranked by geomean CuTe latency / geomean external-baseline latency over the
three study shapes), each at all three study shapes = 60 variants.

Bar per variant: fastest *correct* alternative on the same GPU, including
Helion Triton and every external baseline the study inventory lists
(ATen, torch.compile, Quack, handwritten, TileGym, SDPA backends). Ratio =
best alternative graph-replay latency / best CuTe graph-replay latency.

## Protocol

* Harness: frozen-tree copy of the study protocol via
  `artifacts/worst20-2026-09-28/campaign.py` (wraps
  `benchmarks/cute/compare_example_backends.py worker`). One fresh process per
  implementation, private compiler caches, `HELION_AUTOTUNE_EFFORT=full`,
  `HELION_FORCE_AUTOTUNE=1`, no budget, fresh 62-bit seed per job, CUDA-graph
  replay median of 5 as the primary timer, eager CUDA-event timing recorded
  alongside. Correctness checked before/after timing and after graph replay.
* Added over the study: cooldown to the worker's start temperature +2C before
  every timed section; pause/stop files per GPU; foreign-process monitor that
  voids and requeues interfered shards; `--pin` for pinned-config ABAB.
* Source for the "before" column: detached worktree
  `artifacts/worst20-2026-09-28/before-source` at 783546b4 (dev HEAD at start).
* GPUs: 4 and 5 only. GPUs 6/7 are in use by another user; 0-3 were in use by
  that user at session start (skill rule: avoid for the rest of the session).
  Each variant's providers are always measured on the same GPU.

## Questions for Jason (collected; to be answered before the goal can be declared met or blocked)

1. **grpo_loss s0/s1 are wrapper-bound.** The measured Helion path is `helion_grpo_loss` → autograd Function → `extract_selected_logits_pytorch` (gather + copy + div kernels) + `grpo_loss_forward` whose host prologue allocates four `torch.zeros([B, L])` (four fill kernels) + the device kernel: 7 graph nodes, 17.2 us device / 24.4 us graph at s0 vs the torch.compile bar of ONE fused Triton kernel (2.13 us device / 8.03 us graph); at s1 the wrapper nodes alone (12.9 us device) exceed the 12.1 us bar. No CuTe-backend change can remove host-side allocations or the example's gather; options are an example change (`torch.empty` for fully written outputs, fold the selected-logit extraction into the kernel) or a shared host-codegen optimization (zeros → empty when the device loops provably cover every element). Which, if any, do you want?
2. **Approximate division for fp16/bf16-narrowed quotients** (HSTU silu gate; swiglu backward now passes without it): Triton emits `div.full.f32` (approx, ≤2 ulp) where CuTe emits IEEE `div.rn.f32`; the remaining HSTU v1 gap (42/70/152 vs 19.5/20.3/33.8 us) is this division. Per your standing rule this is only allowed through the `fast_math` setting or a per-site proof, never a config knob. The per-site proof holds when the quotient is immediately rounded to bf16/fp16 (the approx error is far below half a bf16 ulp) — may the lowering use `div.full` for quotients whose only consumer is a narrowing cast?
3. **Timer quantization (characterized 2026-09-30 08:50 UTC, /tmp/timerq/stairs.py on GPU 5).** The campaign timer (single CUDA-graph replay per CUDA-event pair, do_bench median, L2 flush between replays) reports integer multiples of ~2.03 us at EVERY size: a torch.add graph with profiler device time 1.92/2.37/2.82/3.78/4.45/7.17/12.4/22.4/41.7/80.0 us reads 5.95/6.02/8.00/7.97/10.02/12.06/18.21/28.45/46.88/85.79 us. The step is a GPU-side graph-launch tick (~4-6 us of launch latency plus a 2.03 us staircase), so two kernels on the same step read equal and two kernels 0.4 us apart can read 25% apart; the timer cannot adjudicate a 1% margin below ~200 us. Both sides are measured identically, so the study protocol is fair but blunt. Added a secondary timer to the campaign worker (`device_span`: per-replay span from first kernel start to last kernel end inside the same flushed replay, torch.profiler, 32 ns resolution; multi-kernel graphs keep their inter-kernel gaps) recorded next to graph_ms from 08:48 UTC on (ABAB verify rounds carry both). Question: for variants whose graph_ms sits on the launch floor or within one 2.03 us step of the bar, may the goal be judged on device_span (same regime, same flush, same GPU, both sides), with graph_ms reported alongside? Until answered, goal.json keeps graph_ms ratios and the report shows both. (Measurement physics established 2026-10-02 by impl-graph-overhead, /tmp/agent-reports/impl-graph-overhead.md: the campaign timer is a pure staircase 5.95 + 2.045k us over the kernel span with identical launch-side cost for every backend; the ~1 s sustained do_bench phase runs POWER-THROTTLED on the 850 W B200 (SM clock 1965 -> ~1550 MHz; both attention kernels +21-26%, even the flush memset +20%) while device_span is sampled afterwards as the clock recovers, which is why graph_ms - device_span reads 15-18 us at attention s2; our fa4_alt kernel is slightly more clock-sensitive than cuDNN's (+4% vs +1% unthrottled -> mid-throttle 69.9 vs 67.5 us), which plus one 2.045 us step is the whole 73.47-vs-71.42 margin. 4. **In-place state kernels pay the harness's state clone; the functional baseline does not.** linear attention: the case wrapper (benchmarks/cute/example_cases.py:504) calls `recurrent_step(q, k, v, state.clone(), alpha, beta)` because the Helion kernel mutates `state` in place, so every graph replay carries a memcpy node for BOTH Helion backends while torch.compile's functional lowering writes a new state inside its own kernels. s0: cute 10.08 vs torch.compile 8.06 us on the graph timer, device spans 4.06 vs 4.16 (cute faster). s2: cute replay 44.83 = a 24.2 us clone of the 67 MB state + a 17.2 us kernel, vs torch.compile 40.74 = 22.1 (pointwise) + 14.5 (gemv); the Helion kernel alone is faster than both of torch.compile's kernels together, and even a roofline kernel (16.8 us) could not pass with the clone inside the replay (impl-linattn-3.md). Within graph-replay timing an in-place kernel cannot be timed without either the restore copy or letting the state drift across replays (which breaks the harness's post-measurement correctness check), so a harness fix would have to separate the correctness call (with the clone) from the timing call (drifting scratch state, kernel time is value-independent) for every provider alike, and the before numbers for linattn would be re-measured the same way. Alternatively the device span minus the clone node is already recorded. Which number do you want for in-place kernels?

Under the standing rule (approximations only via fast_math or a per-site proof) these knobs should either be gated behind fast_math or accepted explicitly as 'within the bf16 tolerance the examples check'.
